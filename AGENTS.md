# Firecube (AGENTS.md)

This repo is a **batch ingestion worker** for EO datasets that writes Zarr/Parquet and maintains a product-local `.firecube/` control-plane root used for idempotency, resume safety, cleanup, and write coordination.

## Quick start

- For full test suite: `uv sync --extra test`
- Install deps: `uv sync`
- Run CLI: `uv run firecube --help`
- Tests: `uv run pytest`
- Lint: `uv run ruff check .`
- Format check: `uv run ruff format --check .`
- Type check: `uv run pyright`

Before running the test suite, install the CLI integration test fixture plugin:

```bash
uv pip install -e tests/fixtures/firecube_test_plugins
```

This is required for `tests/integration/test_ingest_command_typed.py` and related CLI tests.

## CLI requirements (explicit, no inference)

The CLI infers storage settings from the URI scheme for commands that take a
product URI (`file://`→local, `s3://`→s3; driver defaults to `fsspec`). Pass
`--storage-type` and `--storage-driver` explicitly to override.

**All flags below are required explicitly:**

- `--product-name <name>` — logical product name (or set `PRODUCT_NAME` on your plugin class)
- `--target <uri>` — where to write the output product
- `--write-mode [staged|direct]` — write strategy (NOT inferred from local vs remote)

Write-tier commands require `--write-mode`, except `zarr multires` (which
derives pyramid levels in place) and `zarr consolidate-time-coord` (which
mutates a single existing array in place and has no staging path).

**Removed behaviors (migration required):**
- `output_name` no longer inferred from target URI basename — use `--product-name` or plugin `PRODUCT_NAME`
- `write_mode` no longer defaults to `direct` for local targets — pass `--write-mode` explicitly
- `--input-data` no longer takes a bare or relative path — pass a `file://` URI
- Config key `default_output_name` is rejected — use `default_product_name` instead

**Product name precedence:** CLI `--product-name` > config `default_product_name` > plugin `PRODUCT_NAME` > hard fail.

`--source`/`--target` are always strict product URIs; `--archive`/`--output`
are always strict artifact URIs. `--config-file`, `--target-dir`, `--workspace`
and the `--output` of `firecube completion` are exempt from the strict-URI policy.
They are local paths.
`tests/unit/test_cli_completion.py` pins the `completion --output` behaviour.

`--input-data` is a source URI. It takes `file://`, `s3://` and
`stac://<host>/<api-root>/collections/<id>` values through
`parse_and_validate_source_uri`. It may be repeated, and the schemes may be
mixed. An empty value counts as no `--input-data`. The plugin receives each
admitted URI as given. A plugin that needs a local path calls
`local_path_from_target` from `firecube.core.api`.

One function admits every storage URI option and argument of the CLI:
`parse_and_validate_uri` in `src/firecube/cli/_uri_policy.py`. It accepts lowercase
`file://` and `s3://` only, and refuses `stac://`. A `file://` URI names no host, `localhost`
included, and a path below the root. An `s3://` URI names a bucket. The
function refuses a `?`, a `#` and a control character. It uses the `file://`
path literally and does not decode `%20`. Source options (the `--input-data` of
`ingest`, `zarr preallocate` and `zarr slots`) admit a `stac://` value through its
sibling `parse_and_validate_source_uri` in the same module, which returns a
`StacCollectionUri` (`src/firecube/core/discovery/_types.py`) for `stac://` and
otherwise exactly what `parse_and_validate_uri` returns or refuses. `stac://` is a
source scheme only: `StorageUri` never holds it. A command without a STAC branch
refuses a `StacCollectionUri` in its body with a `click.UsageError` before any I/O.

## Where things live

- Plugin contract: `src/firecube/ingestor/runtime/base.py` (`BaseIngestor`) and `src/firecube/ingestor/contracts/interfaces.py` (Protocols).
- Engine/pipeline runner: `src/firecube/ingestor/runtime/engine.py`.
- Public surfaces for plugins: `src/firecube/ingestor/api.py` and `src/firecube/core/api.py` (prefer these over deep imports).
- External plugins: installed via entry points under `firecube.plugins`; plugin-specific usage belongs in each plugin repository.
- Storage/fs: `src/firecube/core/filesystem/` + `src/firecube/core/storage/` (fsspec-based facade).
- Storage driver abstraction: `src/firecube/core/filesystem/` — `StorageFilesystem` Protocol + `FsspecFilesystem` + `ObstoreFilesystem`. Optional capabilities are Protocols in `protocol.py` that a driver reports through `capabilities()` (both drivers report `AtomicPublish`; obstore also `Multipart`, `RangedRead`; fsspec also `Multipart`). `AtomicPublish.publish_atomic(dst_uri, write)` makes a concurrent reader of `dst_uri` see the old or the new object: a local target gets a hidden reserved temporary beside it (`src/firecube/core/filesystem/publication.py`, `is_publication_temp` keeps in-flight temporaries out of listings and out of staged-metadata seeding) renamed onto it afterwards, existing permission bits kept, temporary removed if `write` or the rename fails; a remote target is written directly because a PUT or completed multipart upload is already whole. `src/firecube/core/storage/session.py` hands a write to it when the driver reports it, else writes in place. Use `create_filesystem(config)` factory. `ZarrStoreFactory` in `store_factory.py`. All I/O goes through the chosen driver — no mixing.
- Optional obstore dep: `src/firecube/core/filesystem/_obstore_compat.py` — import guard. Install: `uv pip install 'firecube[obstore]'`.
- URI helpers: `src/firecube/core/uris.py` (protocol detection, file:// normalization).
- Source discovery: `src/firecube/core/discovery/`. `discover(request)` is the one door. It takes a `DiscoveryRequest` and returns `SourceItem`s. A caller reaches a module behind it only through the package.
  - `_walk.py` is the file-tree backend for a local path, a `file://` prefix and an `s3://` prefix. `_stac.py` is the backend for a `stac://` source. `_registry.py` maps a scheme to its backend. A scheme with no backend raises `UnknownSourceSchemeError`.
  - `_filters.py` checks `input_filters` and `stac_search`. `errors.py` holds the refusals, all `DiscoveryError(FirecubeError, ValueError)`: `StacSearchError`, `StacApiError`, `StacAssetHrefError` and `UnknownSourceSchemeError`.
  - `_stac_compat.py` guards `pystac-client`, the optional `stac` extra, as `_obstore_compat.py` guards obstore. It does not import `pystac_client`. The backend imports it inside the functions that search, after `require_stac`.
  - The STAC backend reads every result page. Its paging rule is `_follow_next_links` in `_stac.py`. It skips an empty page and ends only at a page without a `next` link. It raises `StacApiError` for a `next` link that repeats an earlier request. It raises it also for 5 empty pages in a row (`MAX_CONSECUTIVE_EMPTY_PAGES`). The error says the results may be incomplete. No other paging failure has its own refusal.
  - `discover` deduplicates on `SourceItem.identity` and the first item wins. The identity of a STAC item is `collection/item_id/asset_key`, each part with `%` written `%25` and `/` written `%2F`. `discover` drops a later item with the same identity.
  - `firecube.core.formats` no longer serves `discover_input_files` or `KNOWN_EXTENSIONS`. The modules `firecube.core.formats.discovery` and `firecube.core.formats.input_filters` no longer exist. Import from `firecube.core.discovery` or `firecube.core.api`.
- Reading a source in a run: `WorkspaceManager.materialize` in `src/firecube/ingestor/runtime/workspace.py` takes four kinds of source and returns a local path. A local path and a `file://` href (its literal path) return the file itself. An `s3://` href and an `http://` or `https://` href are downloaded. A `SourceItem` is read by its `href`, never by `SourceItem.scheme`.
  - An `http://` or `https://` href goes through `download_http_source` in `src/firecube/core/filesystem/ops.py`. It makes one GET with no Range request, sends no credentials, and writes the cache file. It does this whatever driver the run's storage uses, because source-side reads are outside the one-driver rule (`plans/STYLE.md`).
  - `StorageUri` never holds `http` or `https`, as it never holds `stac://`. `open_source_filesystem` and the file-tree walker do not take them, so a tree over http is not listed.
  - A scheme other than `file`, `s3`, `gs`, `memory`, `http` and `https` raises `UnsupportedSourceSchemeError` (`src/firecube/ingestor/errors.py`, fields `href` and `scheme`). The change adds no support for `gs` or `memory`.
- Zarr maintenance: `src/firecube/core/zarr/validation.py`, `src/firecube/core/zarr/scrub.py`, `src/firecube/core/zarr/state.py`, `src/firecube/core/zarr/multires.py`
  - `zarr multires` takes `-g/--group`, `--lat-name` and `--lon-name` (`src/firecube/cli/zarr/_multires.py`, passed through `MultiresConfig`). Without `-g`, and with `/` or `""`, the group is the root. Levels go to `<group>/multires/<res>deg`, or to `multires/<res>deg` at the root. `--lat-name` and `--lon-name` default to `lat` and `lon`. Before any write, `src/firecube/core/zarr/layers.py` refuses a named coordinate that is missing, not 1-D or not on its own dimension, with a `ConfigurationError` whose text is a `Message`. The command renders it as a `click.ClickException`, exit 1. Core does not discover coordinate names from CF attributes (`plans/DESIGN.md`).
  - `zarr validate` finds the time dimension of a group in three steps. It takes the `--time-dim` value, then the `firecube_timestamp_state` array, then a rank-1 array whose attributes mark it preallocated or coordinate-managed (`_marked_time_coord_dim` in `validation.py`, over `resolve_coord_lifecycle`). A disagreement between the given name and the state array still raises. A report that checked no array is not valid (`is_valid` is false) and carries a `Message` note that names `--time-dim`. `run_scrub` calls the same detection. It has no CLI command, and its deletion rule is unchanged.
- Coordinate materialization (single-writer time coords): `src/firecube/core/zarr/coord_materialization.py` — engine-owned; the zarr CLI is a thin caller.
  - Every writing path of coordinate materialization is in this module. Payload goes through `_write_coord` under `_hold_coord`. Attributes and markers go through `writer.update_array_attrs`. Creation goes through `writer.ensure_group`.
  - A calendar coordinate is written in this order: the checks, the `units` and `calendar` attrs, the values, then `firecube_preallocated` and the identity hash. A refused check writes nothing.
  - The read-only checks are in `coord_rematerialization.py`. The pure helpers are in `_coord_common.py`.
- Coordinate re-materialization checks: `src/firecube/core/zarr/coord_rematerialization.py` — `check_regular_coord_rematerialization`, `check_irregular_coord_rematerialization` and `RegularCoordTarget`. The module writes nothing. A relabel of stored data raises `CoordinateRelabelError(SchemaDriftError)` with the fields `coord_path`, `stored`, `incoming` and `differs_in`.
- Shared coordinate helpers: `src/firecube/core/zarr/_coord_common.py` — `existing_array`, `array_schema_mismatches`, `build_regular_coord_attrs`, `build_irregular_coord_attrs`, `values_all_nat` and `open_existing_root_read_only`. `existing_array` reads by full path from a live root.
- Fill helpers: `src/firecube/core/zarr/_fill.py` — `_fill_value_is_missing`, `_fill_mask` and `_array_is_all_fill`. Compare an array with its fill value only through these helpers. `_fill_values_equal` stays in `region_writer.py`.
- Time package: `src/firecube/core/time/` is internal. It has no re-export and no entry in a public facade. A module imports only the modules listed before it: `_codecs`, `calendar`, `guard`, `gregorian`, `encode`, `canonical`, `convert`, `encoding`.
  - `_codecs.py` — imports the xarray CF time coders on first use.
  - `calendar.py` — calendar names, aliases and classification, and the CF `units` of an axis (`normalise_calendar`, `is_gregorian_like`, `is_gregorian_axis`, `is_calendar_valued`, `derive_regular_axis_units`, `validate_calendar_units`).
  - `guard.py` — `reject_non_gregorian_calendar_value` refuses a value of another calendar at the Gregorian write-time conversions.
  - `gregorian.py` — the Gregorian fast path (`coerce_to_epoch_s`, `gregorian_to_datetime64_ns`). It imports neither xarray nor cftime. An instant outside the `datetime64[ns]` range raises `Datetime64RangeError(FirecubeError, ValueError)` with the field `value`.
  - `encode.py` — `encode_coordinate` puts one value on a declared calendar axis.
  - `canonical.py` — the bodies of `_canonical_coordinate_value` and `_canonicalise_irregular_value`. `index_spec.py` keeps one-line wrappers.
  - `convert.py` — `coord_to_datetime64`.
  - `encoding.py` — `CoordinateEncoding`, `coordinate_encoding_for` and `coordinate_encoding_from_array`. This is the one place that selects the storage encoding from the declared calendar.
  - A non-Gregorian axis stores an encoded `int64` or `float64` coordinate with `units` and `calendar` attrs. `firecube zarr preallocate` writes it once and in full. Ingest verifies it and never creates it.
  - `DuplicateAxisInstantError(FirecubeError, ValueError)` in `src/firecube/core/index_resolve.py` has the fields `coordinate` and `slots`. It reports two values that fall on one instant of the axis calendar.
- Zarr CLI command package: `src/firecube/cli/zarr/` — group wiring in `__init__.py`, one module per command family, shared helpers in `_common.py`.
- CLI URI rule: `parse_and_validate_uri(value, *, param_hint)` in `src/firecube/cli/_uri_policy.py` returns a `StorageUri`. Each refusal is a `click.BadParameter` with `param_hint` (the flag or the argument name) as its hint, so the text reads `Invalid value for '--target': <sentence>`. Command code reads the scheme and the path only from the returned value. `resolve_product_identity` in `src/firecube/cli/_product.py` takes that value. A command admits a value in its body, not in a Click callback, so the order of its refusals does not change.
  - `parse_and_validate_source_uri(value, *, param_hint)` beside it returns `StorageUri | StacCollectionUri`. `admit_input_sources` drops the empty values of `--input-data`, sends every other value through it, and returns them as given. A bare path, another scheme and an uppercase scheme exit 2. `ingest` keeps its check that a `file://` source exists. The check reads the path of the `StorageUri` that the sibling returns. The stac rules themselves are `StacCollectionUri.parse` in `src/firecube/core/discovery/_types.py`, which the STAC discovery backend also uses.
  - `zarr index` keeps `_manager(target: str, product_name)` with a `str` argument. `_manager` admits the value inside, as its first step.
  - `zarr compare` refuses in this order: a bare argument check of A_URI and B_URI first, then the admission and coherence of A, then B. It passes the raw strings to `compare_zarr_stores`.
  - `IngestCommandConfig` calls the same function for `--target` and appends the refusal text to its error list.
  - Core keeps its own helpers for library callers (`src/firecube/core/uris.py`). They accept bare paths and are outside this rule.
- Archive CLI command package: `src/firecube/cli/archive/`. The `archive` group and its `add_command` wiring are in `__init__.py`. Each command family has one module (`_create.py`, `_restore.py`, `_inspect.py` for `info`, `validate` and `list`). Shared helpers are in `_common.py`.
  - `_local_archive` in `_common.py` admits an `--archive` value through `parse_and_validate_uri` and returns the literal path of a local file. It refuses a remote archive and a missing file. `archive info`, `validate` and `list` call it before the zip or tgm dispatch. `restore` calls it on the zip branch. The commands register with `@click.command`, not `@archive.command`. The group imports them, and the other order is circular. `cli/main.py` imports the package eagerly, so these four submodules load at start-up. Each module stays under 500 lines.
- Library operations behind `zarr preallocate` and `zarr slots`: three internal modules, not exported from a facade.
  - `configure_ingestor` in `src/firecube/ingestor/runtime/configure.py` configures a plugin without a Click context or CLI invocation. A Python caller runs it first. It raises `RemovedConfigKeyError` (`src/firecube/ingestor/errors.py`) for a removed config key and imports no Click. It reads `template_config_class` and `plugin_config_class` with `getattr`, so a plugin that declares neither counts them as `None`.
  - `preallocate_product` in `src/firecube/ingestor/runtime/preallocate.py` performs the whole preallocate.
  - `plan_slots` in `src/firecube/ingestor/runtime/slot_plan.py` computes the whole slot plan. It uses the interval algebra in `src/firecube/core/zarr/planning.py`.
  - Progress goes through the `report` and `warn` callables, never straight to stdout or stderr. Preallocate also hands each dry-run group to `on_dry_run_group`.
  - `_preflight_coordinates` in `preallocate.py` runs the coordinate refusals of every group. It runs under the coordinate-materialization claim, after the store writer is built and before `ensure_resolved_index` publishes. A preflight refusal preserves the Zarr documents and payloads. Claim acquisition and failure recording still change `.firecube/`.

- Index record operations behind `zarr index rebuild` and `zarr index verify`: `src/firecube/ingestor/runtime/index_record.py`, internal, not exported from a facade. `rebuild_index_record` takes `report` and `warn` callables, calls them at the points where the command echoed to stdout and stderr, and records the run terminal or failed afterwards, so output order against run finalization is the command's. `verify_index_record` returns a frozen `IndexVerification` and loads the plugin only through the `load_plugin` callable the caller passes, after the record checks. Refusals raise `IndexRecordError` (a `ConfigurationError`); a `ResolvedIndexConflictError` propagates after the run is recorded failed. No Click, no `firecube.cli` import. Both functions take a `configure` callable that returns the `PluginContext` handed to `index_spec`. Without it the context carries no options. The CLI (`src/firecube/cli/index.py`) keeps plugin lookup, the manager, rendering and exit codes, and imports the module inside the commands. `zarr index verify` and `rebuild` take `--option KEY=VALUE`, repeatable, and configure the loaded plugin through `_configure_ingestor_for_cli` before `index_spec` runs. `--option` without `--plugin` is a `click.UsageError`.
- Time-coordinate consolidation: `consolidate_time_coords` in `src/firecube/core/zarr/coord_consolidation.py`, beside coordinate materialization. Progress goes through `report`. The function refuses an s3 storage config itself and reads live metadata: the root and every descendant group are opened with `use_consolidated=False`, so a stale consolidated snapshot at any level cannot hide a `firecube_coord_managed` stamp. Store-state conflicts raise `SchemaDriftError`, caller input `ConfigurationError`, an invalid product identity `ProductIdentityError` (the CLI maps it to `click.UsageError`, exit 2). Its writes (`create_array`, `shutil`, `os.rename`, attributes) bypass `guarded_write` and `MetadataAuthority` and take no claim (`plans/TODO.md`, the `consolidate-time-coord` entry); do not copy that pattern. The CLI keeps options, URI policy, the `--chunk-size` check, the s3 refusal, the storage config, the dry-run summary and exit 1 when a group is blocked by drift. A backfilled consolidated WAL event is queued while the groups are scanned and reported only after `record_time_coord_consolidation` succeeds for it, so a failed refresh or record prints no line and the rerun prints it once.
- Archive operations behind `archive create` and `archive restore`: `create_archive` and `restore_archive` in `src/firecube/ingestor/runtime/archive.py`, internal, not exported from a facade.
  - Both are keyword-only. They take a `StorageSession` bound to the product, the archive reference the run records, the local archive path and `archive_format` (`"zip"` or `"tensogram"`). `create_archive` also takes the keyword-only `holder_run_id` (default `None`). It names the owner of the product's exclusive maintenance claim, and the maintenance record carries it in its scope meta. Restore takes no such keyword.
  - Both report through `warn`, and restore also reports through `report` for its `restored group: <group>` lines. `warn` receives each whole line, `Warning: ` included.
  - The module owns admission through the maintenance claim (`_acquire_maintenance_claim`, list-then-claim), the run ids (`archive-create-<uuid4>`, `archive-restore-<uuid4>`), the recording and the release order.
  - Restore drives `SpanRecorder`. It records the run started before it touches the target. It tries to record every failure and then raises it. If recording a failure raises, the operation warns through `warn` and still raises the original error. An interrupt (`SystemExit`, `KeyboardInterrupt`) leaves the run started.
  - Create takes a claim and records a run only for a product (a store with `.firecube/schema.json`). A plain Zarr store stays a pure read.
  - Results are frozen. `ArchiveCreateResult` has `archive_format`, `target`, `file_size_bytes`, `run_id` (`None` for a plain store) and `tgm_summary`. `ArchiveRestoreResult` has `run_id` and `summary`.
  - Errors are `FirecubeError` subclasses with fields. `ArchiveClaimError(product, operation)` reports a refused admission. `ArchiveRecordError(archive, product_uri)` reports that create wrote the archive and then failed to record it.

The archive is a run of its own, `archive-create-<uuid4>`, inside the exclusive claim of the release. A release archive is a full backup when the current release retains no zip archive or `archive_full` is set. Otherwise it is an incremental backup against the inventory of the current release, which is its previous release. The incremental backup holds every new or changed object and every Zarr metadata document. The marker lists the `deleted_keys`. `_refuse_unrestorable_deletes` refuses an incremental backup that deletes a key which `deleted_key_problem` refuses, before the inventory is written. Every archive is written from the keys of the frozen inventory, never from a fresh listing, and each entry is checked against the inventory digest. `retention_text` is in this module. `verify_retention` returns a frozen `RetentionVerification`. It reads the local archive files directly, outside the product session. `release.py` calls it through call-time imports.
- Version retention: `src/firecube/ingestor/runtime/release_versions.py`, internal, beside `release_retention.py`. `versions_retention` builds the step for `--retain-versions`. `preflight_version_retention` moves the refusals of that step ahead of the stamp. `verify_versions` checks a release that retains object versions. `verify_retention` calls it at call time, and `release.py` imports the other two at call time.
- Object versions: `ObjectVersions` in `src/firecube/core/filesystem/protocol.py` is a runtime-checkable capability with `bucket_versioning`, `list_versions`, `head_version` and `lifecycle`, and the frozen `ObjectVersion`. `FsspecFilesystem` reports it from `capabilities()` only when the product protocol is `s3`. The obstore driver does not report it, because obstore 0.11 has no version listing (`plans/TODO.md`). `list_versions` reads every page and returns delete markers. `head_version` sends `VersionId` and never opens the object through s3fs `open(version_id=)`, which sets `IfMatch`. A key comes from the `Key` field, never from a name with a `?versionId=` suffix. `--retain-versions` refuses a bucket whose versioning is not `enabled` and an object whose current version id is missing, empty or `null`.
- Literal session delete: `StorageSession.delete_literal(uri)` in `src/firecube/core/storage/session.py` deletes the one object at `uri` through `_literal_delete`. It expands no glob character and removes nothing below `uri`. A driver without a single-object delete raises `StorageError`. A missing object raises on a local store and not on s3. `StorageSession.delete` is recursive and is not for this.
- Archive package: `src/firecube/core/archive/` holds the ZIP code in `zip/` and the Tensogram code in `tensogram/`. The `__init__.py` files import nothing third-party. `_common.py` holds `clear_target`, which the ZIP restore and the Tensogram restore share. No Tensogram module imports a ZIP module.
- Zip archive marker: `MARKER_ENTRY` (`firecube-archive.json`) in `src/firecube/core/archive/zip/marker.py` is a reserved root entry of a zip archive. `marker.py` also holds `MODE_FULL`, `MODE_INCREMENTAL`, `read_zip_marker`, `marker_problem` and `deleted_key_problem`. It imports neither `archive.py` nor `backup_chain.py`. The marker holds exactly eight keys: `version`, `mode`, `previous_release`, `previous_backup_uri`, `previous_backup_digest`, `inventory`, `metadata_manifest` and `deleted_keys`. `zarr_to_zip` in `archive.py` takes the keyword-only `keys` (archive only these product keys) and `marker` (written as canonical JSON). A product key with the reserved name, or a `keys` value outside the product, raises `ValueError`. Without `overwrite`, `zarr_to_zip` publishes through `os.link`, so a lost race clobbers nothing, and a filesystem without hard links fails (`plans/TODO.md`). `zip_to_zarr`, `validate_zip` and `_walk_live` never treat the marker as a product key. A root `zarr.json` is required of a full backup and not of an incremental backup. `read_zip_marker(path)` returns the parsed marker or `None`, and raises `ValueError` for an unreadable or non-object marker. `zip_info` returns it under `marker`, and `archive info` prints it.
- Backup chain restore: `src/firecube/core/archive/zip/backup_chain.py`, internal, no Click. `resolve_backup_chain(path)` follows the markers from the newest backup down to a full backup and returns a list of `ChainBackup` (fields include `previous_release` and `deleted_keys`). It checks every backup before it writes anything. The checks cover the previous backup file, its digest, the entry safety and CRC, and the marker keys. The chain holds at most `MAX_CHAIN_BACKUPS` backups. Each of the `deleted_keys` must stay under the product and outside `.firecube/claims/` (`deleted_key_problem`). `marker_problem` holds the whole marker check, and `validate_zip` applies it too. A failure raises `BackupChainError(FirecubeError)` with the fields `archive`, `broken_at` and `reason`. `restore_archive` resolves the backup chain before it opens its claim and run, so a refused backup chain writes nothing. The restore summary lists the applied versions under `backup_chain`. `restore_backup_chain` puts the full backup. For each incremental backup in order it deletes the `deleted_keys` first, then puts the entries. A replacement key can so take the place of a deleted key or of its directory, as in a Zarr array whose rank changes. It deletes through `StorageSession.delete_literal`, deletes the empty directories a deletion leaves on a local target, and reads every restored object back against its archive entry. It refuses a local target with a symlink on a restored key. A failure in the middle leaves a partial target with no rollback (`plans/TODO.md`).
- Migration steps: the built-in step `firecube:set-attrs` is in `src/firecube/ingestor/runtime/migrations/set_attrs.py`, registered in `pyproject.toml` under `firecube.migrations`. `load_migration_steps` in `src/firecube/cli/plugins/registry.py` reads that entry-point group without importing a step. The executor takes it as the `load_steps` callable, as `index_record.py` takes `load_plugin`.
- Maintenance CLI packages: `src/firecube/cli/snapshot/`, `src/firecube/cli/migrate/` and `src/firecube/cli/release/`, one module per command family and shared helpers in `_common.py`. The groups are registered in `src/firecube/cli/_groups.py`, and `main.py` lists them in a Maintenance section of the root help. Every product-bound command requires `--product-name` and has no fallback. The commands print a structured warning through `render`, imported from `src/firecube/cli/_errors.py`. They map `FirecubeError` to `click.ClickException(render(exc))`.
- Span `arrays`: a `GenericZarrIngestor` span lists time-indexed data variables only (static ones are excluded in `src/firecube/ingestor/runtime/zarr/append_services.py`). For spans written before that, `delete-span` skips arrays lacking the time dimension and warns once per span; unknown dimensions are refused. A `DirectZarrIngestor` span records bare array names and its group in `meta`, and it lists the time coordinate. One resolver turns a recorded array name into its store path (`_span_array_store_path` in `src/firecube/core/controlplane/deletion.py`). It handles three recorded shapes: `<group>/<name>`, `/<name>` at the root, and a bare `<name>` under the span's group. Alignment reads, chunk-key paths and collateral comparison of data arrays go through it. The recorded `state_array` path does not. The code treats it as store-relative and strips only the slashes. `delete-span` keeps a time coordinate that carries `firecube_preallocated` or `firecube_coord_managed`, as promotion does. A span whose `state_array` is absent from the store takes its chunk boundaries from the time-chunk grids of its own arrays (`_expand_ranges_over_grids`). Deletion of chunk records through `_delete_with_filesystem` refuses a key that falls outside the product and deletes the literal object. It never expands glob characters (`_literal_delete`, `_chunk_object_uri`). The span route does not have that guarantee: `delete_spans` still calls `fs.rm(uri, recursive=False)`, which expands glob characters on s3 (`plans/TODO.md`). `chunks delete -n <URI>` deletes through a filesystem bound to that product (`resolve_manager(..., product_filesystem=True)` in `src/firecube/cli/chunks/_manager.py`). It needs no `[storage]` config and ignores a config `target_path`. Runs that name no product URI keep the config path. Scrub deletes through the same filesystem path.
- Guarded payload writes: `src/firecube/core/zarr/guard/guarded_write.py` — the one chokepoint for DirectZarr chunk/shard payload writes (`RegionZarrWriter`, coordinate materialization and engine-owned materialization all call `guarded_write`). It takes the unit locks of `_unit_locks.py` for the whole read-merge-write (or reuses a whole-array lock this thread already holds), applies `write_empty_chunks` to the array handle (`arr.with_config`), never `zarr.config`, and with `track_units` writes through a per-write recording store, so a unit the write deleted is absent, one it stored is not, and a unit with no recorded call gets one existence check after the write; the `WriteResult` reports `absent` (there is no `deleted`) and is handed to `on_result`, still inside the lock. The handle a guarded `write_region` or `write_1d` goes through is read under the unit locks of the write (`reopen` of `guarded_write`), so a handle read before another batch grew the array is never used. The exception is `write_region` in slot-window batches: with `fixed_extent` the writer reuses one handle per array, and a negative slot is normalised against that cached extent. There pod startup creates each array at its full slot count and no batch grows it, but growth by another process during the run (for example `preallocate` run again with a larger slot count) is not detected. Do not write payloads to a DirectZarr store any other way. `WriteFootprint` (`src/firecube/core/zarr/guard/unit_ownership.py`) is the (canonical array path, cell box) a write may change.
- Metadata authority: `src/firecube/core/zarr/guard/metadata_authority.py` — within the guarded DirectZarr layer, `zarr.json` (shape, attrs, markers) is changed only under a `MetadataAuthority` whose basis is `CLAIM` (a held cross-process claim) or `PROCESS_LOCAL` (this process's threads only). Every op checks the authority (active, same store, node in scope) before it touches the store. The editing ops (`create_or_open_array`, `set_attributes`, `update_document`) read the node fresh, edit and write inside one node-lock hold, so a stale handle is never written; `publish_document` instead replaces the whole document without re-reading (it can erase a marker the payload lacks), and `publish_document_if_absent` writes only where none exists. `publish_raw(authority, store, path, data, *, expect)` replaces one v3 or v2 document. It does so only while the stored bytes have the digest `expect`, or while no document exists for `ABSENT`. The node lock decides. Otherwise it raises `DocumentPreconditionError` and writes nothing. The v2 names (`.zgroup`, `.zarray`, `.zattrs`, `.zmetadata`) are admitted only by `publish_raw`, and the other ops admit `zarr.json` only. GenericZarr's own `zarr.json` writes (including its staged seeding, which writes plain files without an authority) are outside this layer. Ops: `ensure_group`, `create_or_open_array`, `set_attributes`, `publish_document`, `publish_document_if_absent`, `publish_raw`, `update_document`; the module also exports `hold_authority` and `adopt_held_claim`. PROCESS_LOCAL cases: legacy (pre-marker) time coordinate, static marker stamp when no claim is held, control-plane loser recovery mirrors (`ChunkManager._write_root_mirror`), staged workspace seeding, promotion metadata publication, root/ancestor creation (`ensure_group_ancestors`; preallocation's `_ensure_ancestors` in `src/firecube/ingestor/runtime/preallocate.py` uses CLAIM only when the run holds the materialization claim). Fallbacks to PROCESS_LOCAL: setup without a control plane (`chunk_manager is None`), strategy and library calls that pass no authority (the writer's default `RegionZarrWriter.authority`). Node locks are leaves: a stored-unit lock may be held while a node lock is taken, never the reverse.
- Write session: `src/firecube/ingestor/runtime/zarr/write_session.py` (`ZarrWriteSession`: prepared → writing → publishing → terminal) + `src/firecube/ingestor/runtime/zarr/direct_region_adapter.py` (`DirectRegionAdapter`: per-batch engine-owned, declared-target, window and ledger checks). `DirectZarrIngestor._verify_schema_at_pod_startup` builds a session for every DirectZarr run kind (serial, slot-window, staged), and a run without one is refused (`ConfigurationError`). Each batch with a pod-written intent runs inside `session.admit_write()` (a batch with no intents, or only engine-owned ones, returns before it and is never admitted); `verify_promotion()` and `close()` stop new admissions and drain batches in flight within `drain_timeout`. A `close()` whose drain times out waiting for in-flight batches or session operations raises `WriteSessionStateError` naming the stuck count, and the failure is remembered: every later or concurrent `close()` raises the same error while work is in flight and returns normally once nothing is. Both authorities (seeding, publishing) are still revoked by the first `close()`. After a failed close the host keeps its session reference; when workspace cleanup is enabled `run()` then skips deleting the staged workspace and logs one ERROR naming its path (the operator removes it once the writes stop); with cleanup disabled (the default) the workspace is never deleted and the failed close is logged as a warning only; and the next run on the host closes the previous session first and is refused while it is stuck. The standard engine joins its workers before it closes, so this is a safety net.
- Staged promotion (DirectZarr): `StorageSession.plan_promotion` / `publish_plan` (`src/firecube/core/storage/session.py`) with the pure planner `src/firecube/core/zarr/guard/promotion_plan.py` publish a delta instead of the workspace tree: PUT every workspace object of a unit the ledger proves written (never compared with the target), DELETE only units the staged ledger proves written and the chokepoint reported absent (never time-coordinate, static or engine-owned units), and compare only non-metadata objects the run did not claim: byte-identical ones are UNCHANGED, the rest are PUT with reason `unclaimed` (a metadata object, `zarr.json`, gets reason `metadata` whether changed or unchanged, and counts as unchanged when it is byte-identical or the target's document supersedes it). A data object of a managed time coordinate is neither PUT nor compared. The plan lists it UNCHANGED with reason `engine-managed` and never asks `is_unchanged` about it. Seeding copied it into the workspace, and `zarr preallocate` may have filled the target since. The coordinate's own `zarr.json` keeps reason `metadata`. The rule covers only the configured time coordinate (`time_dim_name`), and only when its final-target `zarr.json` marks it preallocated or coordinate-managed (`resolve_coord_lifecycle`). No other array is classified, marked or not. A legacy or absent time coordinate takes the path above, because its `unclaimed` PUT is how a staged run's timestamps reach the target. An invalid marker state raises `SchemaDriftError` with the target untouched. `ZarrWriteSession._managed_coordinates` (`src/firecube/ingestor/runtime/zarr/write_session.py`) classifies two sets. One is the coordinates seeding reported (`note_seeded_coordinates`). The other is the coordinate of each group the run wrote, when the workspace holds it. It reads one target `zarr.json` per candidate. `StagedPromotionUnits.managed_coordinates` carries the result into the planner. A written unit under a managed coordinate raises `ValueError` in the planner (`StorageError` at `_promote`). `_promote` (`src/firecube/core/storage/completion.py`) refuses (`ConfigurationError`, target untouched) when such an unclaimed PUT is a data object of an array in the ledger (`unclaimed_data_objects`), for example from a reused workspace. In a staged run that is not a slot window, a batch's negative `ts_index` is made absolute once, against the workspace array's length, before the batch records its footprint (`DirectRegionAdapter.absolute_slots`; `ConfigurationError` if the workspace lacks the array or the slot lies before its first); a staged slot-window intent with a negative `ts_index` raises `WriteIntentRangeError` instead. The written ledger covers only successful contiguous pod-written `region` and `1d` intents (`staged_footprints`); `timestamp` intents never enter the footprint ledger, and a strided region is touched but never recorded as written. `zarr.json` last and only after every data op succeeded. A delete removes one literal object key (no glob expansion); a driver without such a delete refuses a plan that deletes. A target longer on axis 0 keeps its extent, and only then are structural differences refused (an equal-extent difference such as dtype is not checked). A unit the workspace array ends inside (its stored chunk or shard extends past the workspace extent) is proved written only up to that extent, so when the write session builds the promotion units, `require_target_within_clipped_units` (`src/firecube/core/zarr/guard/unit_ownership.py`) reads that array's shape from the target's `zarr.json` and refuses (`ConfigurationError`, target untouched) if the target is longer on an axis where the unit is clipped: promotion replaces the whole object and would erase target cells the run never wrote. Units wholly inside the workspace extent are never checked; a missing, equal, shorter or different-rank target promotes as before. Residual window: a target that grows between the check and the put is not detected; closing it needs a cross-process claim. A unit a run writes entirely as fill replaces (deletes) the old target object only when the handle does not keep empty chunks (`write_empty_chunks=True` stores it). `GenericZarr` is unchanged: it keeps `upload_tree` and its metadata seeding.
- Engine hooks for staged runs: `src/firecube/ingestor/contracts/interfaces.py` defines five one-method Protocols: `_SparseWindowRefusal` (`_refuse_sparse_staged_window`), `_IncompleteUnitsRefusal` (`_refuse_incomplete_staged_units`), `_StagedSeedingAuthority` (`_staged_seeding_authority`), `_SeededCoordinates` (`_note_seeded_coordinates`) and `_StagedPromotionUnits` (`_staged_promotion_units`). The engine checks each hook independently (`isinstance`), so a host may implement any alone. The engine's `_zarr_pre_batch_hook` calls `_note_seeded_coordinates(workspace, paths)` with the coordinate paths seeding copied. A host without the units hook promotes the whole tree. Internal, not plugin contract.
- Staged-write metadata seeding: `src/firecube/ingestor/runtime/zarr/staged_metadata.py` (core helper) + `src/firecube/ingestor/runtime/zarr/batch_runner.py` (`seed_staged_metadata_pre_batch` hook). Honored uniformly for any template that runs in `write_mode="staged"` with `seeds_staged_metadata=True` — no per-template wiring required. The runtime engine invokes seeding before `_process_batch()` for all Zarr outputs. For DirectZarr the seeded workspace `zarr.json` documents go through `publish_document_if_absent` (group/array) and `update_document(..., lambda _current: data)` (root) under the session's PROCESS_LOCAL authority over the workspace (`staged_seeding_authority`); the root document is written only when its bytes differ from the seeded ones. A batch that finds it unchanged does no rename. Without an authority the plain-file path compares the bytes itself. GenericZarr passes none and seeds as before. Seeding also returns the coordinate paths it copied. The engine hands them to the host (`_SeededCoordinates`, in the engine-hooks bullet above).
- CF-packed payloads in GenericZarr: the append path (the view of `_append_write_view`) and the region path (`ds_region`) of `src/firecube/ingestor/runtime/zarr/write.py` send the payload through `decode_cf_packed_payload` in `src/firecube/ingestor/runtime/zarr/schema.py`. The call reads the store being written, never the preflight compare store.
  - A time-indexed data variable whose attrs carry a CF key must match the stored keys, values and dtype, or `SchemaDriftError` is raised before any write.
  - `ConfigurationError` refuses a packing outside the float64 bounds. The refused cases are:
    - an integer wider than 32 bits, a packed float, and a dtype that is neither integer nor floating
    - a zero or non-finite `scale_factor`, and a non-finite `add_offset`
    - 2^b·|scale_factor| + |add_offset| > 2^1000, and 4·2^b + |add_offset/scale_factor| > 2^50
    - a `_FillValue` that differs from `missing_value`, and a CF value that is not a scalar
  - A matching variable is decoded with the stored values (a `scale_factor` or `add_offset` makes the decode run in float64), and xarray re-encodes it to the same raw integers. A variable without CF keys in its attrs reaches xarray unchanged.
  - Neither call passes `encoding=`, because xarray refuses it for an existing variable.
- Metric schema and emission: `src/firecube/core/observability/metrics.py` (canonical schema `RUN_SUMMARY_SCHEMA`, `TelemetryService`, domain-collector key constants).
- CPU/wait accounting: `duration_cpu_s` is process-wide CPU (all threads, user+sys) measured once over the processing window via `time.process_time()` in `PipelineRunner.run_state` — NOT summed from per-batch `time.thread_time()`, which only sees the orchestrating thread and undercounts CPU spent in dask/HDF5/netCDF worker threads (observed ~5× on SEVIRI ingests, making a CPU-bound run look I/O-bound). `non_cpu_wait_s = max(processing_wall_s - cpu_s, 0)`; it is `0` when CPU-bound. Per-batch `PipelineResult.cpu_time_s` stays `thread_time`-based and is a diagnostic lower bound only.
- Tracing facade helpers: `src/firecube/core/observability/tracing.py` (`span`, `set_current_span_attribute`, `capture_context`/`attach_context`/`detach_context`, `propagated_context`).
- Observability boundary enforcement: `tests/unit/test_observability_boundaries.py` (mirrors `test_no_raw_fsspec_usage.py`; covers OTel, Prometheus, logging-handler boundaries).
- CF-1.8 Tier-1 advisor: `src/firecube/core/cf/` — check IDs (`check_ids.py`), report dataclasses (`report.py`), structural validator (`validator.py`). Surfaced via `firecube advise compliance --profile cf-18`.

### Plugin contract requirements
- Plugins may use `firecube.ingestor.api`, `firecube.core.api`, and supported optional `firecube.ingestor.extensions` capabilities. Core utilities remain domain agnostic; plugins own product interpretation, filename conventions, grouping, coordinate meaning, quality rules, and published metadata. Pattern parsing does not select sources or interpret time fields.
- Every concrete `BaseIngestor` subclass must declare `PRODUCT_NAME: ClassVar[str]` — enforced at class-definition time via `__init_subclass__`. Abstract templates (e.g. `GenericZarrIngestor`) are exempt.
- `PipelineResult.metrics` is typed `ResultMetrics` (not a plain dict). `PipelineResult.outputs` is `OutputPaths` (not a plain dict). Both are importable from `firecube.ingestor.api`.
- Plugins must not construct `PipelineResult(output_path=...)` — use `PipelineResult(outputs=OutputPaths(primary=...))`. The legacy kwarg was removed and raises `TypeError`; the read-only `result.output_path` property remains for readers.
- Plugins may declare `time_dim_name: ClassVar[str]` on their `BaseIngestor` subclass to control the firecube append/index dimension name written into the Zarr store; default is `"timestamp"`. Mirrors the `PRODUCT_NAME` pattern. This is NOT a config-tier field and is NOT exposed via `--option`. The runtime engine consumes this name to seed coordinate-array chunks in staged mode so that plugin value-based timestamp resolvers (e.g. `resolve_timestamp_index`) see real coord values instead of NaT on re-ingest.
- DirectZarr parallel plugins declare `index_spec(ctx) -> IndexSpec | None` on the plugin. `None` means serial mode. A non-`None` spec opts into engine-owned slot-index resolution.
- If a plugin returns an `IndexSpec`, it must also implement `inspect_item(item, ctx) -> ItemInfo | None`. The engine uses that mapping to place each item in the resolved index.
- `ItemInfo(coordinate=..., values={array name: scalar})` supplies the per-slot value of an engine-owned array; `values` is never hashed (`hash=False`, not in the schema hash); its content is persisted as the engine-owned array, the mapping object is not. `ZarrArraySpec(engine_owned=True)` is valid only for rank-1 time-indexed arrays (otherwise `ValueError`) and not for the time coordinate. Use it for per-slot scalars instead of letting pods write them: pods never write engine-owned arrays.
- Pod-written time-indexed arrays that declare neither `chunks` nor `shards` are created with time chunk 1 (zarr's own whole-array chunks when they already have it; otherwise the per-slot default plus one warning logged when firecube changes zarr's choice; shards-only declarations keep their shards); declare `chunks=` to choose a layout. A slot window must cover whole stored units of every pod-written time-indexed array; plugins need not align anything for arrays created by this default.
- Plugins must not rely on `SUPPORTS_SLOT_RANGE_PARALLELISM` or `slot_index_model()`. Those mixin-era hooks were removed with the clean cut.

### Plugin-specific CLI helpers (optional)
- Core CLI hosts plugin utilities under `firecube plugins <plugin> ...` when a plugin registers a Click group under the `firecube.plugin_cli` entry-point group (e.g. in `pyproject.toml`: `[project.entry-points."firecube.plugin_cli"]` with `my_plugin = "my_plugin.plugin_cli:cli"`). Merely creating a `plugin_cli` module is not enough — the entry point must be declared.

## Gotchas / debugging

- If JSON logs are required, disable progress logging (`--option no_progress=true`) to keep stdout machine-readable.
- If ingestion "hangs" at 0% with parallel execution, set `--option pipeline_workers=1` to isolate locking/IO contention (DuckDB, HDF5).
