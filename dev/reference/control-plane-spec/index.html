    Control-Plane Specification

    This page specifies the on-disk format of the .firecube/ control plane that Firecube maintains next to every product it writes. It is a format specification, not a guide: a reader with no Firecube installation can parse .firecube/ from this page alone. The key words MUST, MUST NOT, and MAY are normative.

    Two format versions apply, and every JSON document carries its own schema_version field:

    Surface Version
    Control-plane envelope: schema.json, run records, WAL events, compact cache, LATEST.json v2
    Index records: index/current.json, slot_index/current.json v1
    Metadata snapshots: manifests, records and metadata/refs/latest.json v1
    Release records and the release ref: every document under releases/ v1
    Inventories: releases/inventories/<hash>.json v1
    Migration journal: runs/<run_id>/plan.json v1

    Layout

    The control plane lives inside the product root, in a directory named .firecube. All paths below are relative to that directory.

    .firecube/
    schema.json                  Control-plane format descriptor, written once
    runs/<run_id>/run.json       Run record, one directory per run
    runs/<run_id>/events-NNNNN.jsonl   WAL segments for that run, NNNNN from 00000
    runs/<run_id>/plan.json      Migration journal, only for a migration run
    claims/<digest>.json         Write claims, one file per claimed write domain
    compact/compact-<generation>.jsonl       Projected chunk records
    compact/compact-<generation>.meta.json   Compact cache metadata
    compact/compact.lock         Lock file of a local rebuild
    compact/LATEST.json          Pointer to the newest compact cache generation
    index/current.json           Resolved-index record
    slot_index/current.json      Slot-index model record
    metadata/blobs/sha256/<aa>/<hex>   Bytes of one metadata document, <aa> the first two digits of <hex>
    metadata/manifests/<hash>.json     Path-sorted list of the documents of one snapshot
    metadata/records/<hash>.json       One snapshot event
    metadata/refs/latest.json          Pointer to the newest snapshot record
    releases/<key>.json          Release record, one file per release version
    releases/refs/current.json   Pointer to the current release
    releases/inventories/<hash>.json   Inventory of the objects of the product at one cut

    Only the directories a product has used exist. A serial ingest without a declared index has no index/ directory. A product with no compact cache rebuild has no compact/ directory. A product with no snapshot has no metadata/ directory. A release run creates the releases/ directory when it first writes a release file. A release run that retains chunk bytes creates the releases/inventories/ directory when it writes the inventory. A run that fails or stops after that write can leave an inventory that no release record names. That file is harmless, and Firecube does not remove it.

    Earlier releases wrote snapshots/snapshot-<generation>.jsonl, snapshots/snapshot-<generation>.meta.json and a LATEST.json at the root of .firecube/. Firecube writes none of them now. Firecube ignores them on read. A reader MUST NOT use them. An operator MAY delete them.

    Atomicity

    Writers publish every control-plane JSON document atomically, except the compact pointer. A reader that can see a file MUST be able to parse it as complete JSON. Writers publish through a temporary object followed by an atomic rename (local filesystems) or a conditional put (object stores).

    Some writes create a file and never replace it. schema.json, claim files, index/current.json, slot_index/current.json and release records fail when the file already exists. The journal plan.json fails too, unless the existing file holds the same bytes.

    The blobs, manifests and records under metadata/ are content-addressed. A writer that finds one present leaves it as it is and does not fail. Two snapshots of unchanged metadata share one manifest. Inventories under releases/inventories/ follow the same rule.

    run.json is replaced atomically in place because peer processes read it while the run is live. The pointers metadata/refs/latest.json and releases/refs/current.json are replaced atomically in place.

    The compact pointer compact/LATEST.json is the exception. A rebuild writes it in place with a plain write. A reader can see an incomplete pointer during that write.

    schema.json

    Written once, when the first run initializes the control plane. Never rewritten.

    Key Type Meaning
    schema_version string "v2"
    layout string "chunkmanager-v2"
    created_at number Unix timestamp (seconds) of first initialization

    Run Records

    Each run owns the directory runs/<run_id>/. Its run.json is the run's liveness and resume record, heartbeat-refreshed while the run is active.

    Key Type Meaning
    schema_version string "v2"
    product string Logical product name
    run_id string Run identifier, equals the directory name
    status string Run status; terminal states are recorded by WAL events
    parts integer Number of sealed WAL segments
    events integer Total WAL events written so far
    started_at number Unix timestamp (seconds)
    updated_at number Unix timestamp of the last heartbeat
    run_uri string Absolute URI of the run directory
    run_stale_threshold_s integer Seconds after which a silent run counts as stale
    error string Present only on failure
    completed_at number Present only after completion
    slot_range array Present only for slot-range parallel runs: [start, end)
    slot_group string Present only for slot-range parallel runs

    A run whose updated_at is older than run_stale_threshold_s MAY be treated as abandoned by recovery tooling. See Recover a Product.

    Producer record: meta.producer

    A run records which software produced it. The record is the object meta.producer in the meta of the WAL events listed below. It is not a key of run.json. Firecube captures it once, when the run starts.

    Run kind Events that carry meta.producer
    Ingest run_started and run_failed
    Preallocate run_started, run_completed and run_failed

    An ingest run_completed event does not carry it. No span event carries it. No other run kind records it. A reader MUST treat an absent meta.producer as unknown.

    Key Type Meaning
    schema_version integer 1
    captured_at string ISO 8601 UTC timestamp of the capture
    plugin object The plugin that ran, see below
    source object Where the plugin code came from, see below
    firecube object version: the Firecube version string
    config object The digest of the run configuration, see below

    The plugin object has these keys:

    Key Type Meaning
    name string Registered plugin name
    distribution string or null Name of the installed distribution that provides the plugin
    version string or null Version of that distribution
    entry_point string or null Value of the firecube.plugins entry point that loads the plugin

    The source object has these keys:

    Key Type Meaning
    kind string vcs, editable, wheel or unknown
    commit string or null Commit identifier
    requested_ref string or null Branch, tag or revision that the installer requested
    dirty boolean or null Whether the working tree has uncommitted changes
    evidence array of strings The facts that Firecube read to decide the other keys

    The four values of source.kind mean:

    • vcs: the distribution was installed from a version-control URL. commit is the installed commit. dirty is false when commit is set, else null.
    • editable: the distribution is an editable install. commit and dirty come from Git in the source directory. Each is null if Git cannot answer.
    • wheel: the distribution was installed from an archive or a built directory, or it has no direct_url.json. commit and dirty are null.
    • unknown: Firecube found no distribution for the plugin. It is also the kind when the direct_url.json is unreadable, is not JSON, is not an object, or has no recognised source metadata. commit and dirty are null.

    The config object has these keys:

    Key Type Meaning
    algorithm string "sha256"
    digest string Hash of the canonical JSON of the engine, template and plugin configuration
    canonicalization string "firecube-config-json-v1"
    excluded array of strings Dotted paths of the values left out of the digest

    The digest leaves out each configuration field that has repr=False, each free-form x_* key, and each value with no JSON form. Storage credentials are not in the digest input.

    A null value means unknown. It never means false or absent. A dirty of null means that Firecube could not check the working tree. Firecube sets dirty to false only when it has evidence.

    WAL events

    The write-ahead log is the authoritative, append-only record of what happened to the product. Events are JSON objects, one per line, in segment files events-00000.jsonl, events-00001.jsonl, and so on under the run directory. Segments are immutable once sealed. Every event carries this envelope:

    Key Type Meaning
    schema_version string "v2"
    event_id string Unique event identifier
    event_type string One of the event types below
    product string Logical product name
    run_id string Emitting run
    timestamp number Unix timestamp (seconds)
    record object Event-type-specific payload
    meta object Optional; omitted when empty

    Event types:

    event_type Emitted when
    run_started A run begins
    run_started_with_replacement A run begins and will replace existing chunks
    run_completed A run ends successfully
    run_failed A run ends with an error
    run_abandoned A stale run is marked abandoned
    span_committed A write span commits
    span_failed A write span fails
    span_noop A write span is skipped as already satisfied
    record_replaced A chunk record is replaced
    record_upsert A chunk record is inserted or updated
    replacement_committed A replacement transaction commits
    maintenance_started A maintenance operation begins
    maintenance_completed A maintenance operation ends successfully
    maintenance_failed A maintenance operation fails
    schema_verification A store schema check is recorded
    index_ensured A resolved index is written, matched, rebuilt, or refused
    slot_index_model_recorded A slot-index model record is first written
    slot_index_model_verified An existing slot-index model record is verified
    consolidated_time_coord A time-coordinate consolidation rewrites an array

    The index_ensured payload records run_id, product, identity_hash, the sorted axis_kinds and groups of the declaration, an ISO 8601 timestamp, and an outcome that is one of created, matched_existing, conflict_refused, or rebuilt.

    Claims

    A claim grants one owner exclusive write access to a write domain, identified by the string product:category:name. The claim file name is the SHA-256 hex digest of that identifier, so claim lookup never requires listing: claims/<sha256(product:category:name)>.json.

    Key Type Meaning
    product string Logical product name
    domain string The product:category:name identifier
    owner_id string Claim owner
    claim_path string Absolute path of this claim file
    acquired_at number Unix timestamp (seconds)
    last_heartbeat_at number Refreshed by the owner while held
    heartbeat_interval_s number Owner's refresh cadence
    stale_threshold_s number Staleness cutoff, default 120

    Semantics:

    • Acquisition is the atomic creation of the claim file. If the file already exists, acquisition MUST fail with a claim conflict; it MUST NOT take over the claim, even a stale one.
    • Release deletes the file.
    • A claim is stale when now - last_heartbeat_at > stale_threshold_s. A crashed owner leaves a stale claim behind. Operators clear stale claims with firecube chunks claims clear, which refuses to clear fresh claims unless forced.
    • Abandoning a run releases every claim whose owner id resolves to that run alone. The release applies to fresh and stale claims. The claim file stays in place if its owner or acquired_at changed after the claims were listed.
    • An owner id resolves through its candidates: the id itself and each prefix that ends just before a :. The claim is released only if exactly one candidate is a recorded run, and that run is the abandoned one.
    • A sweep of stale runs also releases the claims of a run that an earlier abandon already ended. A sweep that a crash interrupted therefore finishes its release when it runs again.
    • The firecube chunks runs abandon --all-stale sweep releases a claim of a terminal run only if the claim is stale when re-read before the delete. Its dry run reports the claims it would release and the claims it would leave.
    • If the claims of the product cannot be listed, the abandon reports an error and does not report success. Run the abandon again to release the claims.
    • Acquisition does not change. A claim that the release left in place still blocks acquisition of its domain.

    Known limitation: a release reads the claim again, then deletes the file. These are two separate operations. If two releases run at the same time, one can delete a claim that a successor acquired between the read and the delete. firecube chunks claims clear has the same limitation. Do not run two releases for the same product at the same time.

    Exclusive maintenance claim

    The domain <product>:maintenance:exclusive is the exclusive maintenance claim of a product. It is a claim like any other, and the rules above apply to its file. Its owner_id is the id of the maintenance run.

    • A conforming writer MUST NOT write to the product while another owner holds this claim. A stale claim counts as held.
    • A writer MUST refuse if it cannot read the claim file.
    • The check reads the one claim file by name, claims/<sha256(<product>:maintenance:exclusive)>.json. It passes when the file is absent or when its owner_id is the id of the writer.
    • A writer makes the check when it starts, when it takes its admission claim, and when it ensures the resolved index.
    • The writer records a run start that the check refuses. The run has a run_started event and one run_failed event with the refusal text, and no other terminal event. If the failure record cannot be written, the run has no run_failed event.
    • A migration or a release repeats the check before every document write. An absent claim passes.
    • The commands zarr multires and zarr consolidate-time-coord make the check once, when they start. They take no claim and use the owner ids multires-<uuid4 hex> and consolidate-<uuid4 hex>.
    • A maintenance operation that runs under its own exclusive claim records the id of the holder in the key holder_run_id. The key is in the meta object of the maintenance event record and in maintenance.scope.

    See Write Safety for how claims coordinate concurrent writers.

    Compact cache

    The compact cache is a projection of the WAL into one chunk record per line. Readers use it to avoid a replay of every run's events. A rebuild writes compact/compact-<generation>.jsonl with the records sorted by key. It then writes the sibling compact/compact-<generation>.meta.json. Last, it updates compact/LATEST.json to point at the new generation. <generation> is a nanosecond timestamp, so generations sort chronologically.

    compact-<generation>.meta.json and compact/LATEST.json both carry schema_version ("v2"), generation, completed_before and product. completed_before is a Unix timestamp. The cache folds in the runs that completed before this instant. The pointer adds snapshot_path and snapshot_meta_path. The meta file adds created_at and records, the line count. The keys keep their snapshot_ names. Their values name files under compact/.

    A local rebuild holds compact/compact.lock while it writes. A rebuild on an object store takes no lock.

    If the pointer is absent, a reader replays the WAL. A store that has only the earlier layout therefore reads from the WAL. The compact cache is derived data. An operator MAY delete the compact/ directory at any time. A rebuild creates the cache again from the WAL.

    Resolved Index: index/current.json

    The resolved-index record is the durable form of an engine-resolved IndexSpec. It is written once, after the first successful resolution, and verified against the plugin declaration on every later run. Inspect it with firecube zarr index show; regenerate it with firecube zarr index rebuild. The rendered API reference for the record type is ResolvedIndexRecord.

    Key Type Meaning
    schema_version string "v1"
    recorded_at string ISO 8601 UTC timestamp
    recorded_by_run_id string Run that wrote the record
    identity_hash string 64-character lowercase hex SHA-256, see below
    index object The resolved-index payload
    items array Present only for discovered axes: content-addressed item manifest, sorted by coordinate value

    Identity hash

    The identity hash content-addresses the resolved index. Canonical bytes are the UTF-8 encoding of the payload serialized as JSON with sorted keys, separators (",", ":"), and ensure_ascii=false.

    • Without items: identity_hash = sha256(canonical_bytes(index)).
    • With items: the hash covers {"index": index, "items": items} with items sorted by their per-item identity_hash, so the value is invariant under input order and changes whenever an item is added or removed.

    The same hash is mirrored into the Zarr root attributes firecube_resolved_index (the payload) and firecube_resolved_index_identity_hash, so a store detached from its control plane still carries its identity.

    Precedence rules

    On every run, the engine compares three things: the control-plane record (index/current.json), the mirrored attrs hash on the store, and the index resolved from the current plugin declaration. The rules are exhaustive and evaluated in this order:

    Row Record Attrs hash Relation Outcome
    1 absent absent fresh store write record and attrs, outcome created
    6 present any record schema_version is not v1 refuse: manifest error
    2 present present both match the declaration outcome matched_existing
    3 present absent record matches the declaration re-mirror attrs, outcome created
    4 absent present attrs without a record refuse: manifest error
    5 present any record disagrees with the declaration refuse: resolved-index conflict
    7 present present record matches, attrs disagree refuse: manifest error

    Refusals surface as documented control-plane errors, never as silent overwrites. Row 5 is the guard against pointing a changed declaration at an existing store. Use the plugin that wrote the product, or a new target. firecube zarr index rebuild does not change this row.

    For row 4, restore index/current.json. Or remove the root attrs firecube_resolved_index_identity_hash and firecube_resolved_index, then run firecube zarr index rebuild with the plugin that wrote the data. For row 7, remove the root attr firecube_resolved_index_identity_hash, then run firecube zarr index rebuild. The command writes the attr again from the record. rebuild refuses both states while the attrs remain.

    Slot Index: slot_index/current.json

    Products using slot-index models carry a parallel record with the same envelope discipline: schema_version ("v1"), recorded_at, recorded_by_run_id, identity_hash, and model. The model's canonical bytes cover name, epoch, time_unit, and the per-group axes (cadence and mode) with sorted keys; the identity hash is the SHA-256 of those bytes and is mirrored to store attributes the same way as the resolved index.

    Maintenance operations

    A maintenance event carries the operation as a string in record.maintenance.op and in record.meta.op. The accepted strings are scrub, delete, archive_create, archive_restore, migrate, adopt and release_create. The last three belong to the metadata maintenance commands:

    op Run id prefix
    migrate migrate-
    adopt adopt-
    release_create release-

    The meta object of a migrate event also carries step_id, distribution, version, journal, allow, outcome, before_snapshot, overrides, to_release and resumed_from. journal is the store-relative path of plan.json.

    Metadata snapshots: metadata/

    The directory metadata/ holds four kinds of file. Every id is 64 lowercase hex digits. A blob holds the exact bytes of one metadata document, with no envelope and no schema_version. Manifests, records and refs/latest.json are canonical JSON: sorted keys, no spaces, UTF-8. Each carries schema_version "v1".

    Path Content Id
    blobs/sha256/<aa>/<hex> The bytes of one document, as read <hex> is the SHA-256 of the bytes. <aa> is its first two digits.
    manifests/<hash>.json The list of the documents of one snapshot <hash> is the SHA-256 of the file.
    records/<hash>.json One snapshot event <hash> is the SHA-256 of the file. It is the snapshot id.
    refs/latest.json The newest snapshot Not content-addressed. A writer replaces it in place.

    A reader MUST check that the bytes of a file hash to its id.

    A writer MUST NOT rewrite a blob, a manifest or a record. A writer MUST NOT delete one, because snapshots share these objects. A writer publishes a snapshot in this order: the blobs, the manifest, the record, and last refs/latest.json. A writer that stops before the last step leaves a valid record that refs/latest.json does not name.

    A manifest lists the Zarr node documents (zarr.json, .zgroup, .zarray, .zattrs, .zmetadata) of every group and array. It also lists .firecube/schema.json, .firecube/index/current.json and .firecube/slot_index/current.json. A manifest lists no other path of .firecube/.

    A manifest has the key documents, an array sorted by path. Each entry has these keys:

    Key Type Meaning
    path string Store-relative path with / separators and no leading slash
    digest string sha256: followed by the hex digest of the bytes. The hex digest names the blob.
    size integer Length of the document in bytes
    kind string v3_group, v3_array, v3_unparsed, v2_group, v2_array, v2_attrs, v2_consolidated, firecube_schema, firecube_index or firecube_slot_index

    A record has these keys:

    Key Type Meaning
    schema_version string "v1"
    parent string or null Id of the record that refs/latest.json named when the snapshot was taken
    manifest string Id of the manifest
    run_id string or null The owner of the exclusive maintenance claim for a coherent snapshot, else null
    trigger string Why the snapshot was taken, for example migrate-before
    taken_at number Unix timestamp (seconds) at which the capture started
    consistency string coherent or observation
    scope object included_kinds: the sorted list of document kinds that the capture reads

    A writer makes a coherent snapshot only while it holds the exclusive maintenance claim. It reads the claim before and after the capture. If the owner changed or the claim is gone, the writer refuses and writes nothing.

    refs/latest.json has the keys schema_version and snapshot. The value of snapshot is the id of the newest record.

    Releases: releases/

    releases/ holds one record per release version and one pointer.

    The file name of a record is <key>.json. <key> is the version with these changes, applied in this order:

    1. % is written %25.
    2. / is written %2F.
    3. A leading . is written %2E.

    The empty version has the key %. The record keeps the version verbatim in its key version. A reader MUST take the version from the record, not from the file name. A reader MUST refuse a record whose version encodes to another key.

    A release record has these keys:

    Key Type Meaning
    schema_version string "v1"
    version string The release name, verbatim
    created_at number Unix timestamp (seconds)
    previous string or null The version that was current when the record was written
    snapshot string Id of the coherent snapshot that the release names
    runs_since_previous array of strings Ids of the runs that started after the previous release was created, oldest first
    producer object or null The meta.producer object of the latest run that records one, else null
    producer_status string recorded when producer is an object, else unknown
    note string or null Free text given when the release was created
    created_by_run string Id of the release_create run, or of the migrate run that created the release
    retention object Optional. What the release retains of the objects of the product, see below. A record without the key retains nothing.

    The key retention is additive on v1. A reader MUST treat a record without it as a release that retains nothing. A reader that finds the key with a value that is not an object MUST refuse the record. A writer omits the key for a release that retains nothing.

    The object retention has the key kind. The value is zip or s3-versions. The other keys depend on the kind.

    For the kind zip, the release keeps the objects in a ZIP archive on a local file system:

    Key Type Meaning
    kind string "zip"
    uri string file:// URI of the archive
    format string "zip"
    size_bytes integer Length of the archive in bytes
    digest string sha256: followed by the hex digest of the archive file
    mode string full when the archive is a full backup of the inventory, incremental when it holds the changes since the previous release
    previous_release string or null Version of the release whose archive this archive extends, null for a full backup
    chain_length integer Number of archives in the backup chain, from this one down to the full backup, both included. A full backup has the length 1.
    deleted_key_count integer Number of keys of the previous inventory that this inventory no longer lists. A full backup has the count 0.
    inventory string Id of the inventory that the archive was written from
    created_by_run string Id of the archive_create run that wrote the archive

    A full backup holds every object of the inventory. An incremental backup holds each object that is new or whose digest differs from the previous inventory. It also holds every Zarr metadata document (zarr.json, .zgroup, .zarray, .zattrs, .zmetadata), whatever its digest. The names of the deleted keys are in the archive, in the reserved root entry firecube-archive.json, not in the record. That entry also names the previous release, the previous archive and its digest.

    The marker firecube-archive.json is a JSON object with exactly these eight keys. A reader MUST refuse a marker with a missing key or an extra key:

    Key Type Null for a full backup Meaning
    version string No Version of the release that the archive retains. It is not empty.
    mode string No full or incremental. The same value as retention.mode.
    previous_release string or null Yes, required Version of the release whose archive this archive extends. An incremental backup needs a non-empty string.
    previous_backup_uri string or null Yes, required The retention.uri of the previous release. An incremental backup needs a non-empty string.
    previous_backup_digest string or null Yes, required The retention.digest of the previous release, in the form sha256: and 64 lowercase hex digits. An incremental backup needs this form.
    inventory string No Id of the inventory that lists the objects of the archive. It has 64 lowercase hex digits.
    metadata_manifest string No Id of the manifest of the snapshot that the release names. It has 64 lowercase hex digits.
    deleted_keys array of strings No, the array is empty Keys of the previous inventory that the current inventory no longer lists. The keys are unique.

    A full backup has null in the three previous_* keys and an empty deleted_keys array. A key in deleted_keys must not be empty or absolute. It must not hold a backslash or a character from U+0000 to U+001F or U+007F. It must not have an empty, . or .. segment. It must not name a file below .firecube/claims/ or the entry firecube-archive.json.

    For the kind s3-versions, the release keeps no bytes. It records the version of each object, which the bucket must keep:

    Key Type Meaning
    kind string "s3-versions"
    inventory string Id of the inventory that lists the versions
    bucket_versioning string The versioning state of the bucket at the cut, always enabled
    object_count integer Number of objects in the inventory, delete markers not counted
    created_by_run string Id of the release_create run

    The pointer refs/current.json has the keys schema_version and version. The value of version is the version of the current release.

    A writer MUST NOT rewrite or delete a release record. A writer publishes a release in this order:

    1. The root attributes firecube_release and firecube_last_modifier.
    2. The consolidated image, if the store has one.
    3. The snapshot, which therefore contains the stamps and the image.
    4. The inventory, only for a release that retains objects.
    5. The archive, only for the kind zip.
    6. The record.
    7. The pointer refs/current.json.

    A record that refs/current.json does not name is an earlier release or a release whose publication did not finish. An inventory or an archive that no record names is the leftover of a release whose publication did not finish. A writer MUST NOT reuse a leftover archive. A leftover inventory is harmless.

    Inventories: releases/inventories/

    An inventory lists the objects of the product at the cut of one release. The file name is <hash>.json. <hash> is the SHA-256 hex digest of the file, and the record names it in retention.inventory. The file is canonical JSON: sorted keys, no spaces, UTF-8. A writer MUST NOT rewrite or delete an inventory. A reader MUST check that the bytes of the file hash to its name.

    An inventory has these keys:

    Key Type Meaning
    schema_version string "v1"
    kind string digest for the kind zip, s3-versions for the kind s3-versions
    objects array One entry for each object, sorted by key, without a repeated key
    bucket_versioning string Only for s3-versions: the versioning state of the bucket, always enabled
    lifecycle object or string Only for s3-versions: the lifecycle rules of the bucket, {} when it has none, or "unavailable" when the rules could not be read

    Each entry of objects has these keys:

    Key Type Meaning
    key string Path of the object relative to the product root, with / separators. It has no empty, . or .. segment.
    size integer Length of the object in bytes. A delete marker has the size 0.
    digest string Only for digest: sha256: followed by the hex digest of the bytes
    version_id string Only for s3-versions: the current version of the object
    etag string Only for s3-versions: the ETag of that version, when the bucket reports one
    delete_marker boolean Only for s3-versions, and only true: the current version of the key is a delete marker

    A digest inventory lists every object below the product root, including the files below .firecube/. It leaves out .firecube/claims/ and the temporary objects of the writers of Firecube. An s3-versions inventory lists the current version of each key under the same exclusions. A key whose current version is a delete marker has an entry with delete_marker set.

    The inventory records the product at the cut, before the release run completes. A restored backup chain reproduces the inventory. It does not reproduce the completed live product. The writer publishes records after the cut. These include the inventory of the release, the release record, the new current pointer and the completed state of the release run. The archive step also records its own audit run. None of them is part of the archive of that release. The inventory of the next release includes the release record of the previous release.

    A writer refuses a key that it cannot record literally and writes no inventory. On a local product, the writer also refuses a regular file that the storage driver does not list. On s3-versions an object with no usable version id also stops the release. Such an object was written before the bucket enabled versioning.

    No storage backend lists a prefix atomically. A write that lands between the first and the last listed object makes the inventory incoherent. An inventory is coherent only while the operator keeps every other writer of the product stopped. The exclusive maintenance claim excludes the writers of Firecube and no other process. Firecube does not enforce the stop.

    Migration journal: runs/<run_id>/plan.json

    A writer creates the journal once, before the run writes to the store. A writer MUST NOT change it afterwards. The file is canonical JSON with these keys:

    Key Type Meaning
    schema_version string "v1"
    plan_kind string "metadata"
    run_id string Id of the run, equal to the directory name
    step object id, distribution and version of the migration step
    outcome string executed, or adopted when the store already holds the planned values
    before_snapshot string Id of the coherent snapshot that the plan was made against
    to_release string or null The release that the run creates after the write
    resumed_from string or null Id of the failed run whose plan this run carries on
    overrides array of objects One {"node_path", "key", "class"} object for each attribute of class interpretation or unknown that the run was allowed to change
    documents array of objects The planned documents in write order, the root consolidated image last

    Each entry of documents has these keys:

    Key Type Meaning
    path string Store-relative path of the document
    before string or null sha256: digest of the document before the run, null when it did not exist
    after string sha256: digest of the planned bytes
    image boolean true for the root consolidated image

    The planned bytes are not in the file. A writer stores each planned document as a blob under metadata/blobs/, named by its after digest, before it creates plan.json. An entry whose before equals its after adds no blob, because the before-snapshot already holds the bytes.

    Reserved root attributes

    Firecube reserves six attribute names on the root group of a product. A plugin MUST NOT declare them as root-group attributes.

    Attribute Written by
    firecube_resolved_index Index resolution
    firecube_resolved_index_identity_hash Index resolution
    firecube_slot_index_model Slot-index recording
    firecube_slot_index_model_identity_hash Slot-index recording
    firecube_last_modifier Maintenance operations
    firecube_release Maintenance operations

    firecube_last_modifier is an object. The key operation is migrate or release_create. The key at is an ISO 8601 timestamp. The other keys depend on the operation:

    operation Other keys
    migrate run_id, step_id, distribution, version
    release_create run_id, release

    firecube_release is the release version string.

    Reserved Zarr array attributes

    Firecube stamps a small set of reserved attribute names on the arrays it manages, including the write-once static-array marker firecube_static_written. The authoritative list and the guard helper are in Core Utilities. Plugins MUST NOT write these names.

    Co-location

    .firecube/ and the readable data store are one product. When copying or moving a product manually, the control plane MUST move with the data for inspection, resume, recovery, and cleanup to keep working. Firecube's archive and restore commands preserve it automatically.

    Versioning

    This specification is versioned by the schema_version fields above, and each documented file names its version explicitly. The compatibility rule:

    • Within a version, readers MUST ignore keys they do not recognize; keys MAY be added without a version change, and documented keys keep their meaning.
    • A change that would break a conforming reader (removing a key, changing a type or the canonical-bytes rule) increments the schema_version of the affected document.
    • The move of the cache to compact/, the key meta.producer and the exclusive maintenance claim change no schema_version. The new keys are additive. The compact cache is derived data, and a reader that finds no pointer replays the WAL.
    • The directories metadata/ and releases/, the file plan.json and the maintenance operations migrate, adopt and release_create change no schema_version of an earlier document. Each new document starts at v1.
    • The directory releases/inventories/ and the key retention of a release record change no schema_version. The key is additive, and a record without it stays valid. An inventory starts at v1.
    • A reader MUST refuse a snapshot, release, inventory or journal document whose schema_version it does not support.
    • Firecube refuses to act on an index/current.json whose schema_version it does not support (precedence row 6) rather than guessing.
