# Further Pass Review

Perform a quality review pass over the codebase or specified area.

## Arguments

`$ARGUMENTS` — optional pass number and/or paths. Default pass number is 2.

State the pass number at the start and increase strictness on later passes.

## Pass 1-2: Foundation

- Simplification opportunities: reduce complexity, remove redundancy.
- Naming quality: variables, functions, modules, CLI flags, docs headings.
- Comments and docs quality: accurate, helpful, not redundant.
- Duplicate sources of truth introduced or touched by the change.
- Public API imports stay on `firecube.ingestor.api` or `firecube.core.api`.
- Required formatter, lint, and focused tests run.

## Pass 3-4: Hardening

Everything from Pass 1-2, plus:

- Edge cases and logical regressions.
- Error messages are clear, actionable, and credential-safe.
- Public docs updated and free of internal implementation history.
- No dead code, unused imports, stale TODOs, or obsolete docs.
- Generated or derived artifact drift scan.
- Storage driver and URI behavior remains explicit; no inference slips back in.
- Parallel ingestion, resume, and control-plane behavior fail closed where needed.

### Drift Scan

Every hit must be inspected; these greps are not automatic failures.

```bash
rg -n "generated by|automatically generated|do not edit|Code generated|openapi-generator|swagger-codegen|protoc|bindgen" .
rg -n "TODO|FIXME|Phase [0-9]|commit C[0-9]|reviewer|plans/" docs README.md
rg -n "default_output_name|output_name|infer|basename|storage_type.*s3://|write_mode.*local" src docs tests
```

## Pass 5+: Polish

Everything from Pass 3-4, plus:

- Every changed public function/class has useful documentation.
- Every changed error path has a test.
- Every changed edge case has explicit behavior.
- User docs read as task guidance, not implementation narrative.
- Performance: no avoidable repeated discovery, I/O, serialization, or array copies.
- Consistency: similar patterns are handled the same way across CLI/runtime/docs.
- Clean-room verification for changed packaging, docs, or build flows.

## Process

1. State pass number and strictness level.
2. Scan the requested area or changed files.
3. List findings by category and severity.
4. If asked to fix, implement scoped changes.
5. Verify with:

   ```bash
   uv run ruff check .
   uv run pyright
   uv run pytest <focused tests>
   uv run mkdocs build --strict --site-dir /tmp/firecube-mkdocs-check
   ```

6. Summarize what changed and what the next pass should focus on.
